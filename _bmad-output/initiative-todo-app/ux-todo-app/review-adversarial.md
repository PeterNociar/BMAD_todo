# Adversarial / Edge-Case Review: DESIGN.md + EXPERIENCE.md

**Verdict:** The spines describe each action well when it happens alone and the server answers promptly. Once actions overlap, run on a phone, or run against a long list, a builder is left guessing: optimistic actions on unconfirmed tasks, out-of-order responses, focus-return side effects and the non-sticky input all lack rules, and some of those guesses break FR-2, FR-4 or SM-4.

Counts: 2 critical, 6 high, 6 medium, 2 low.

---

- **[critical]** Actions on a held task whose add has not been confirmed yet (EXPERIENCE § Age Nudge and New-Task Hold, last bullet; § State Patterns "Add rollback"). *Scenario:* Peter presses Enter, then immediately ticks or deletes the held row while the POST is still in flight. The spine says "the action applies immediately", but the task has no server id yet, so the tick/delete request has nothing to target. Worse, if Peter deletes it and the add then fails, add rollback runs on a row that is already gone: a "Couldn't save new task." toast appears for a task he chose to delete, and its text comes back into his empty input. If the add succeeds after the delete was dropped client-side, the task comes back on the next load (breaks FR-13 "does not return after a refresh"). *Fix:* Define an identity and queueing rule. Either use a client-generated id (UUID) accepted by the API, or queue row actions until the add confirms. Also specify the outcome of every pairing: delete then add fails means silent (no toast, no text restore); delete then add succeeds means send the delete; tick then add fails means row removed plus the add toast only.

- **[critical]** Rapid tick/untick and out-of-order server responses (EXPERIENCE § State Patterns "Action error"; § Component Patterns "Tick ring"). *Scenario:* Peter ticks, notices the wrong row and unticks within 300ms. Two requests are in flight. The untick succeeds, then the tick's failure arrives late, and "the row returns to its exact previous state" puts it back as *open*… or as *completed* if the builder snapshots state per request. Either way the UI no longer matches the server. Related gaps: (a) who sets the completed time, the client optimistically or the server? If the server does, the completed group re-sorts when the response arrives, so rows jump with no user action. (b) "Exact previous position" is undefined when other rows moved in the meantime. *Fix:* One in-flight mutation per task, with later intents coalesced or queued (last intent wins, and only the final server state is reconciled). Rollback re-derives position from FR-6 instead of restoring an index. State that the server timestamp replaces the optimistic one without animation unless the order actually changes.

- **[high]** Refocusing the input after every row action opens the phone's soft keyboard (EXPERIENCE § Component Patterns "Tick ring"/"Delete button", § Interaction Primitives "After any task action, focus returns to the input", § Responsive & Platform). *Scenario:* On a phone Peter taps a ring. `input.focus()` inside a tap handler counts as a user gesture on iOS and Android, so the keyboard slides up, the visual viewport shrinks by about half, and the list reflows. This repeats on every tick and delete during UJ-2 backlog clearing. On load, by contrast, iOS will *not* open the keyboard for programmatic focus, so behaviour differs by entry point. *Fix:* Scope FR-2 refocus to non-touch interactions (the PRD says "by mouse or keyboard"). On touch (`pointerType === 'touch'`), do not move focus after row actions and blur the input if it was not already focused. State explicitly that autofocus on load is best-effort on mobile.

- **[high]** The input is not sticky, so focus return, FR-4 and scroll collide on long lists (EXPERIENCE § Information Architecture, § Age Nudge "The page does not scroll to follow it"; DESIGN § Layout & Spacing). *Scenario:* With 500 tasks Peter scrolls to row 300 and ticks it. Focus returns to the input, and the browser's default `focus()` scrolls the page to the top, losing his place on every action. With `preventScroll`, the next Enter adds a task into an input that is off-screen, and the held task is "directly under the input" and also off-screen, which breaks FR-4. The toast layer is also off-screen, so failures go unseen. *Fix:* Decide one of: (a) header, input and toast layer are `position: sticky` at the top of the viewport, with the held row rendered in that sticky zone; or (b) refocus with `preventScroll`, and on Enter scroll the input into view. The spines must pick one; right now they imply both "never scroll" and "always visible".

- **[high]** Toasts cover the held task, and the load-failure toast covers it indefinitely (EXPERIENCE § Component Patterns "Toast", § Age Nudge "Toasts overlay it rather than push it", § State Patterns "Add while loading or after load error"). *Scenario 1:* Peter adds task A, which fails, then immediately adds B. The A-failure toast sits directly under the input exactly where held B is, so B is not visible and FR-4 fails. *Scenario 2:* The list failed to load and the persistent "Couldn't load your tasks." toast overlays the top of the list. Every task Peter adds is held under the input, which is under that toast, and then "slides into its sorted place" in a list area that is blank. His new tasks are hidden for as long as the API is down. There is also no cap on toast count: ticking 10 rows with the server down stacks 10 toasts over the top of the list, covering the rings he is trying to tap. *Fix:* Cap visible toasts (e.g. 2, collapsing the rest into one, or dedupe identical messages with a count). Reserve space instead of overlaying while a held task or a persistent toast is present, or render held rows above the toast stack. Define where post-load-error adds render (a list container holding only those tasks, not "blank").

- **[high]** Merge rules for adds during loading or after a load error are a single [ASSUMPTION] (EXPERIENCE § State Patterns "Add while loading or after load error", "Load error"). *Scenario:* Peter adds X during a slow first load. The GET was issued before the POST, so the response lacks X, and a naive "replace list with response" deletes X from view even though it saved. Or the GET was served after the POST, so X arrives in the response *and* as the optimistic row, producing a duplicate. After a load error, Retry "shows the skeleton again": does the skeleton replace the tasks Peter added meanwhile? What if the 3s hold expires before the list arrives: slide into what? And when the only tasks are ones added during a failed load and Peter deletes them all, is that the empty state (forbidden after load failure) or blank? *Fix:* Specify reconciliation by id (server list ∪ pending optimistic, dedupe by client id). Skeleton rows render *below* any locally added rows, never replacing them. A hold never ends into an unloaded list: it extends until the list arrives. After a load error, locally added tasks show in a list container and the empty state stays suppressed until a load succeeds.

- **[high]** Rapid adds and multiple failed texts break "nothing lost" (EXPERIENCE § Voice and Tone "Override of FR-16", § Open Questions 2, § State Patterns "Add rollback"). *Scenario:* With the API down, Peter types and enters three tasks in 2s. All three fail while the input is empty. Which text returns to the input? If it is "each on failure", the second overwrites the first and the third overwrites the second, so two tasks vanish with no trace, which goes beyond the accepted override (that only covered "user already typed new text"). Open Question 2 leaves held-task stacking undecided, so a builder will pick one at random. Also, the FR-3 length safeguard returns >2,000 characters to the input with a toast that does not say why (Open Question 3), so re-pressing Enter fails forever. And "input is empty" is untested for whitespace-only input or an active IME composition. *Fix:* Close Open Question 2 (recommend: held tasks stack newest-on-top, each settling on its own timer; with reduced motion, instant). For multiple failures, restore only the most recent failed text and name the loss explicitly as accepted, or keep a small failed-text queue. Define "empty" as trimmed-empty with no active composition. Close Open Question 3 with a distinct over-length message, since an identical toast invites an infinite retry loop.

- **[high]** On hybrid devices an invisible delete button can be tapped (EXPERIENCE § Component Patterns "Delete button", § Interaction Primitives "Pointer vs touch"; DESIGN § Components). *Scenario:* On a touchscreen laptop or iPad with trackpad, `(hover: hover)` reports the *primary* pointer as fine, so delete is hidden until hover. It stays "always in the Tab order", so it is hidden by opacity, not removed. Peter touches the right edge of a row to scroll or tap, hits the invisible ×, and the task is permanently deleted with no undo. *Fix:* Show delete whenever `(any-pointer: coarse)` matches, not only when `hover: none`. Or make the hidden state `pointer-events: none`, re-enabled on row hover or focus-within only for `pointerType === 'mouse'`. State this in the spine because the failure is irreversible.

- **[medium]** Enlarged touch hit areas overlap neighbouring rows' delete buttons (EXPERIENCE § Interaction Primitives "Hit areas… extended towards 44px"; DESIGN § Layout "Task row"). *Scenario:* A single-line row is about 8+19+8 = 35px tall. Extending the delete target towards 44px vertically makes it overlap the row above or below. A tap near a divider deletes the neighbour (permanent). *Fix:* Hit areas extend horizontally only, or are clamped to the row box. Alternatively raise the coarse-pointer row min-height to 44px. Pick one explicitly.

- **[medium]** Client clock *ahead* of the server is unhandled (EXPERIENCE § State Patterns "Clock drift"; PRD FR-15). *Scenario:* The spine only covers timestamps in the future (client behind). If the laptop clock runs 90 minutes fast, every add shows "now"/green optimistically, then flips to "1h" and a yellow-green bar the moment the server's added time replaces the client's. Freshly added tasks look stale, and the held task's label jumps during the hold. *Fix:* Estimate the server offset (e.g. from the `Date` header or a `serverTime` field on responses) and compute ages against `Date.now() + offset`. Keep the clamp to "now" as a backstop.

- **[medium]** Wake from sleep and long-hidden tabs (EXPERIENCE § Age Nudge "Live ages"). *Scenario:* Peter closes the laptop lid with the tab visible and opens it two days later. `visibilitychange` often does not fire (the tab never became hidden), and the 30s interval may be deferred, so labels show "20h" instead of "2d" for up to 30s+, and the list is two days stale with no refetch. With bfcache (back, then forward), timers resume and the list may be stale too. *Fix:* Recompute on `visibilitychange`, `focus`, `pageshow` (persisted) *and* whenever the interval detects a wall-clock gap much larger than 30s. Decide whether a long gap (e.g. >1h hidden) triggers a silent refetch and, if so, how it merges without moving focus.

- **[medium]** Focus is lost when a focused toast control disappears (EXPERIENCE § Component Patterns "Toast", § State Patterns "Load error", § Interaction Primitives Tab order). *Scenario:* Peter Tabs to the load-failure toast's Retry and presses Enter. Retry succeeds and "the toast closes by itself", removing the focused element, so focus falls to `<body>` and his next keystrokes go nowhere (breaks FR-2). The same happens when a 5s toast auto-dismisses while its × has keyboard focus. The spine only defines focus return for "closing by pointer". *Fix:* Whenever a toast is removed while it contains focus (for any reason), move focus to the input. Pause the auto-dismiss timer while the toast has focus or hover (WCAG 2.2.1 timing).

- **[medium]** Theme resolution details are missing: first paint, live system change and storage failure (EXPERIENCE § Component Patterns "Theme toggle", § Open Questions 1). *Scenario:* A stored "dark" preference is read after the framework mounts, so the page flashes light first. With no stored choice, the OS switches to dark at sunset mid-session, and nothing says the app must listen to `matchMedia('(prefers-color-scheme: dark)')` changes. In a private window `localStorage` throws, and the toggle may crash. *Fix:* Apply the theme in an inline pre-paint script. Follow live system changes when nothing is stored. Wrap storage in try/catch, falling back to session-only. Close Open Question 1, because otherwise one click locks the user out of "follow system" permanently.

- **[medium]** Refresh or navigation while an add is in flight silently loses the task (EXPERIENCE § State Patterns; PRD SM-4). *Scenario:* Peter presses Enter and immediately hits Cmd+R or closes the tab. The input is already cleared and the POST is aborted. On reload the task is gone, with no toast, because that page no longer exists. *Fix:* While any mutation is pending, register `beforeunload` (native prompt), or persist pending adds to `sessionStorage` and replay them on load. State which one; "nothing silently lost" (PRD §4.6) currently has a hole.

- **[low]** Arrow-key focus on a row that moves or disappears (EXPERIENCE § Interaction Primitives "Shortcuts", § Age Nudge). *Scenario:* Down from the input lands on the held task (the first row). Three seconds later it slides to the bottom of the open tasks, and focus rides along, so the page auto-scrolls away and the next Down goes to the wrong neighbour. Likewise an action-error rollback re-inserting a row above the focused one shifts what "next" means, and the spine never says whether Down from the input targets the held row or the oldest task. *Fix:* Settling a held row that contains focus ends the hold without moving focus, or delays the settle until focus leaves. Arrow navigation is always computed from the current DOM order at keypress time.

- **[low]** Age column width, font swap and consistent time snapshots (DESIGN § Typography, § Components "Age label", `age-column-min: 62px`). *Scenario:* "done 100d" is 9 mono characters at 12px (about 65px), which exceeds the 62px min, so the column misaligns after about 3 months of completed-task history (completed tasks are never archived). The Inter/JetBrains Mono `swap` from fallback fonts changes text metrics and wrapping, so rows jump height after first paint while the input is focused. If label and colour call `Date.now()` separately, a row can momentarily read "1d" with a non-overdue colour. *Fix:* Size the column for the longest realistic label (e.g. `ch`-based width of "done 999d"), or cap the display at "99d+". Use metric-matched fallbacks (`size-adjust`/`ascent-override`) and preload both fonts. Compute label and colour from a single `now` snapshot per render pass.
