# Accessibility review: Todo App UX spines

Lens: accessibility (WCAG 2.1 AA, zero critical axe/Lighthouse violations). Reviewed: `DESIGN.md`, `EXPERIENCE.md`, `.memlog.md`, PRD NFR-1, FR-2, FR-9/10, FR-16..18, `docs/bmad_exercise.md`. Date: 2026-09-30.

## Verdict

**Close to AA, with one conformance blocker and a few gaps.** The colour work holds up: every contrast claim I recomputed matches within 0.01. Colour is never the only cue, reduced motion is covered, and the keyboard model follows FR-2. What stands between these spines and a clean AA pass is behaviour the spines leave unspecified. The `/` shortcut fails 2.1.4 as written. Focus has nowhere defined to go when a focused toast or row disappears. Screen-reader users get no confirmation when an action succeeds. The input, the list and the page landmarks have no semantics set. axe would probably pass a straight build of the spines. A manual AA audit would not.

## Findings

- **[critical]** The `/` shortcut is a single printable-character shortcut that is active "from anywhere outside" the input. It has no way to turn it off or remap it, and it is not limited to one component having focus. That fails SC 2.1.4 Character Key Shortcuts as written. Speech-input users can trigger it by accident. axe will not catch this, but a manual audit will. (EXPERIENCE § Interaction Primitives › Keyboard; memlog keyboard decision.) *Fix:* Esc and Up-from-first-row already reach the input, so drop `/`. Or make it fire only while focus is inside the list, so it counts as active on focus of that component. Or put it behind a modifier (for example Alt+/ or Ctrl+/). Record the choice in the memlog.
- **[high]** Focus has no defined destination when the element holding it disappears. Four cases: (a) a keyboard user is on a toast's close × or Retry when the toast auto-dismisses or closes after a successful retry; (b) the toast is closed from the keyboard, since only pointer close returns focus; (c) a row control has focus while the row re-renders; (d) Retry is pressed and the load succeeds. In each case focus drops to `<body>`, which breaks FR-2 and SC 2.4.3. (EXPERIENCE § Component Patterns › Toast; § State Patterns › Load error.) *Fix:* Add one rule: "whenever the focused element is removed, focus moves to the input". Pause a toast's auto-dismiss while it has focus or hover (focus-within, hover).
- **[high]** Screen-reader users get no feedback when add, tick, untick or delete succeeds. Focus jumps back to the input, the row moves or vanishes, and nothing is announced. Open Question 4 covers add only. Under SC 4.1.3 Status Messages, and in plain usability terms, the user cannot tell the action worked. (EXPERIENCE § Accessibility Floor › Live regions; Open Questions #4.) *Fix:* Use one polite, visually hidden status region. Announce "Added: X", "Marked done: X", "Marked not done: X" and "Deleted: X". Keep it short, and don't announce the move of the held task. Also announce the list becoming empty ("No tasks left") after the last delete.
- **[medium]** The input has no specified accessible name. The placeholder "What needs doing?" is its only label. axe accepts a placeholder, but it disappears once the user types, and some screen reader/browser pairs don't read a placeholder as a name reliably (SC 3.3.2, 4.1.2). (EXPERIENCE § Voice and Tone › Screen-reader labels; DESIGN § Components › Input.) *Fix:* Add a visually hidden `<label>` "New task" (or `aria-label`) to the label table. Add `autocomplete="off"` and `enterkeyhint="enter"` too (see the arrow-key finding).
- **[medium]** List and page semantics are unspecified: `<ul>`/`<li>`, a name for the list, landmarks, the `<title>`, `lang`. DESIGN says "No headings", so axe best-practice rules (`page-has-heading-one`, `region`) will be flagged as moderate. They are not critical, but they add noise to the zero-violations gate. (EXPERIENCE § Information Architecture; DESIGN § Typography.) *Fix:* Specify `<html lang="en">`, `<title>Todo</title>`, `<header>` + `<main>`, the wordmark as `<h1>` (visual style unchanged) and `<ul aria-label="Tasks">` with one `<li>` per task. Set `aria-busy="true"` on the list while it loads.
- **[medium]** Focus handling for the held new task is undefined. If a keyboard or screen-reader user arrows onto the held task during the ~3s hold, the row slides away from under them. If it re-renders, focus is lost. If the held row is placed first with CSS `order`, the DOM order no longer matches the visual order (SC 1.3.2, 2.4.3). (EXPERIENCE § Age Nudge and New-Task Hold.) *Fix:* Make the held row first in the DOM. Key rows by id so the element (and its focus) survives the move. Postpone settling while any control in the held row has focus.
- **[medium]** The reflow target is 360px, but SC 1.4.10 requires 320 CSS px (a 1280px screen at 400% zoom). At 400% zoom a laptop viewport is also only about 190px tall, and the toast overlay plus header plus input could cover most of it. (EXPERIENCE § Foundation, § Responsive; DESIGN § Layout & Spacing › Phone.) *Fix:* State "no horizontal scroll and no loss of function from 320px". Add a 320×256 check to the Playwright a11y suite. There is room: fixed row chrome is about 155px, which leaves about 165px for text.
- **[medium]** Auto-dismissing toasts after about 5s is short for screen-magnifier users. The toast sits under the input, which may be outside their magnified view. It is also short if the user wants to reach the close ×. Info-only toasts pass SC 2.2.1 (there is nothing to act on, and Retry persists), but only just. (EXPERIENCE § Component Patterns › Toast; PRD FR-18.) *Fix:* Pause the timer on hover and focus-within, and on window blur. Consider 6–8s. Never put an action other than close on a timed toast.
- **[medium]** Arrow keys clash with native behaviour. On a single-line text input, Down moves the caret to the end on macOS. Down also opens the browser's autofill history list. The rows are not a composite widget (no roving tabindex or role), so arrow navigation can't be discovered and screen readers in browse mode swallow it. (EXPERIENCE § Interaction Primitives › Shortcuts.) *Fix:* Set `autocomplete="off"` on the input. Only take over Down when there's no autofill popup, which `autocomplete="off"` guarantees. Keep Tab as the documented primary path. Consider a visually hidden hint ("Use arrow keys to move between tasks") linked with `aria-describedby` on the first tick ring.
- **[medium]** The unfocused input border is 1.41:1 on bg (light) and 1.55:1 (dark), and the surface/bg step is 1.10:1 / 1.08:1. When focus is elsewhere (on a row, on the toggle), the input's boundary fails SC 1.4.11. It relies on the placeholder alone, and the placeholder is gone once text is typed. DESIGN marks this as an [ASSUMPTION]. (DESIGN § Colors › Border.) *Fix:* Use `{colors.check-ring}` for the unfocused input border: 3.18:1 light on bg / 3.51 on surface; dark 3.87 / 3.59. Or add a text-muted bottom rule.
- **[low]** Theme toggle: swapping the label ("Switch to dark theme") is correct. Do not add `aria-pressed` as well, because the two conflict. The visual pill shows the current mode while the name gives the action, which is fine. The active segment is only a surface fill (1.10:1 on bg), so the state shows only through icon colour, text-primary vs text-muted (2.81:1 light, 2.37:1 dark). That's acceptable because the name carries the state, but it's weak in forced-colors mode. (DESIGN § Components › Theme toggle; EXPERIENCE › Theme toggle.) *Fix:* Keep the label swap. In `forced-colors: active`, outline the active segment with `CanvasText`.
- **[low]** "Hidden until hover/focus-within" for delete must use opacity (or clip), not `display:none`/`visibility:hidden`. Otherwise it drops out of the Tab order, which contradicts "always in the Tab order". Voice-control users on desktop can't see an unrevealed × to target it. SC 1.4.13 is met, because the revealed control is inside the hovered row and covers nothing. (EXPERIENCE § Component Patterns › Delete button; DESIGN › Delete button.) *Fix:* Specify `opacity:0` → 1 on `:hover`/`:focus-within`. Optionally show delete at low emphasis at all times, as on touch. It already passes at 5.82:1.
- **[low]** DESIGN's contrast table says "delete on hover 5.38". That figure is the icon on the *row* hover tint. The delete button's own hover background is `{colors.divider}`, which gives 4.51:1 light / 4.88:1 dark. It still passes 3:1, but the table should show the worst case. (DESIGN § Colors › Contrast.) *Fix:* Add the row "delete on divider (button hover): 4.51 / 4.88".
- **[low]** The tick ring is a button whose label swaps. That's valid, but screen readers then read the task text twice per row (once in the button name, once as row text). A native checkbox would expose the state more idiomatically. (EXPERIENCE › Tick ring; § Voice and Tone.) *Fix:* Either keep the button and hide the duplicate visible text with `aria-hidden` while the name carries it, or use `<input type="checkbox">` labelled by the task text. The checkbox then announces "checked" or "not checked", and the separate done/not-done wording goes away.
- **[low]** Live age updates: the spec rightly says they aren't announced. Implementation must keep age labels out of any `aria-live`/`role="timer"`/`role="status"` container, or they will be read aloud every 30s. The words form for "now" is not defined ("added just now"? "completed just now"?). (EXPERIENCE § Accessibility Floor; § Voice and Tone.) *Fix:* Add a note that age labels are not live. Add words for "now": "added just now" / "completed just now".
- **[low]** Load-failure retry that fails again: the alert's text doesn't change, so it isn't re-announced. The user presses Retry and hears nothing. (EXPERIENCE § State Patterns › Load error.) *Fix:* Announce "Still couldn't load your tasks." politely on each failed retry.
- **[low]** Live regions must exist in the DOM before messages are injected, or the first toast is often missed. (EXPERIENCE § Accessibility Floor.) *Fix:* Add a note: render empty `role="status"` and `role="alert"` containers on first paint.
- **[low]** Text resize and spacing (SC 1.4.4, 1.4.12). All type is in px, the toggle segments are a fixed 22×18, and line-height is fixed at 1.35. Browser zoom works, but a user's default font size is ignored, and fixed heights could clip. (DESIGN § Typography, § Components.) *Fix:* Use rem for type. No fixed heights on rows, toasts or the empty state. Test with the text-spacing bookmarklet (line-height 1.5, letter 0.12em, word 0.16em).
- **[low, advisory 2.2]** Target size: the visible tick is 16px, delete 20px and the toggle about 22px high. The spec's "hit areas at least 24×24" meets 2.5.8 (WCAG 2.2). On touch the row is about 35px tall, so the goal of reaching toward 44px can't be met vertically (2.5.5 is AAA). (EXPERIENCE › Pointer vs touch.) *Fix:* No change is needed for AA. Make the delete hit area span the full row height on coarse pointers.
- **[low, advisory 2.2]** Focus not obscured (SC 2.4.11, 2.2): toasts overlay the top of the list and can cover the focused tick ring or delete of the first rows, which is where overdue tasks and the held task live. (EXPERIENCE › Toast; memlog toast decision.) *Fix:* Use `scroll-margin-top` equal to the toast stack height on row controls, or dim or shift the toast while a covered control has focus.
- **[low]** Reduced motion covers slides, the settling of the held task, the gap closing after delete, and toast fades. That is complete. The held task still jumps after 3s, which is acceptable. SC 2.3.3 (AAA) is not required. (EXPERIENCE § Motion.) *Fix:* None required. Optionally mention forced-colors: the filled check must stay visible (SVG with `currentColor`), and the age bar may disappear, which is fine because it is decorative.
